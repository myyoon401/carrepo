# 커리포(Carrepo) — 프로젝트 구조 설계

> 백엔드 · 프런트 · 실행/배포를 한 문서에 둔다.
> 확정된 결정과 그 근거만 적는다. 미정은 [미결정](#미결정)에 모은다.

---

## 1. 서비스 정의

지원 공고를 모아두고, 이력서·지원 문구를 만들어 저장하고, 전형 결과까지 쌓아
**다음 지원에 재활용하는 개인 커리어 저장소**.

공고 수집은 외부 채용 사이트에 맡긴다. 커리포가 맡는 것은 **붙여넣은 이후**다.

### 무엇을 해결하는가

지원 자료를 마크다운 파일로 직접 관리하면 네 가지가 깨진다.

| 파일로 할 때 | 커리포에서 |
|---|---|
| 지원 이력 표를 손으로 갱신하다 어느 시점부터 멈춤 | 지원 건 조회로 항상 최신 |
| 이력서 버전이 파일명에만 존재 (`_수정본`, `_최종`, `_v16`) | 버전 행 + 제출본 FK 로 계보가 남음 |
| 초안과 제출본이 다른 파일로 흩어짐 | 제출 시점의 내용을 못 박아 보관 |
| "이 소재를 저번 지원에 썼던가"를 기억에 의존 | 소재 ↔ 지원 건 연결로 추적 |

마지막 항목이 커리포의 존재 이유다. **공고를 저장하는 서비스가 아니라,
과거 지원 데이터를 다음 지원에 재사용하는 서비스다.** 이게 없으면 마크다운 뷰어와 다를 게 없다.

### 사용 환경

**반응형 웹.** 모바일과 데스크탑에서 **기능이 동일하다.** 어느 쪽이 읽기 전용이라거나
특정 기능이 한쪽에만 있지 않다. 공고 등록·문구 작성·이력서 편집 전부 양쪽에서 된다.
화면 폭에 따라 레이아웃만 달라진다.

따라서 화면을 둘로 나누지 않는다. → [4.2](#42-프런트는-하나다)

## 2. 전체 구조

```
carrepo/
├── settings.gradle.kts          include("backend")
├── build.gradle.kts             루트: subprojects 공통 플러그인·의존성
├── backend/                     Kotlin + Spring Boot    (:8080)
│   └── src/main/kotlin/com/carrepo/…
├── web/                         Vite + React            (:5173, dev 전용)
│   ├── package.json
│   └── src/
├── docs/
└── docker-compose.yml           PostgreSQL
```

모노레포 도구(Turborepo·Nx·pnpm workspace)는 **쓰지 않는다.** 패키지가 둘뿐이고
서로 코드를 공유하지 않는다. Gradle 이 backend 를, pnpm 이 web 을 각자 맡는다.

### 2.1 설계 기준

**서버 하나 띄우면 백엔드도 프런트도 다 보일 것.** 이게 모노레포로 가는 유일한 이유다.
구조적 완성도를 명분으로 복잡도가 올라가는 건 거부한다.
판단 기준은 **"혼자서, 프런트가 약한 상태로, 1년 뒤에도 고칠 수 있나"**.

## 3. 실행과 배포

### 개발

```bash
docker compose up -d            # PostgreSQL
./gradlew :backend:bootRun      # :8080
pnpm --dir web dev              # :5173  — /api/* 를 8080 으로 프록시
```

브라우저 코드는 API 주소를 모른다. 항상 같은 출처의 `/api/...` 상대 경로로 부르고,
dev 에서는 Vite 프록시가 8080 으로 넘긴다. **CORS 설정이 필요 없다.**

### 배포

```bash
./gradlew :backend:bootJar      # web/dist 를 jar 의 static/ 에 넣는다
java -jar backend/build/libs/carrepo.jar
```

**산출물은 jar 하나, 프로세스 하나.** 배포에서는 Spring 이 정적 리소스를 직접 서빙하므로
프록시도 게이트웨이도 없다. 연결 비용은 Gradle `Exec` 태스크 한 개(`pnpm build` 실행 + `dist` 복사)
정도다. node-gradle 플러그인은 들이지 않는다.

## 4. 기술 스택

### 4.1 백엔드

| 축 | 선택 |
|---|---|
| 언어 / 런타임 | Kotlin, Java 21 toolchain |
| 프레임워크 | Spring Boot 4.x |
| 빌드 | Gradle, 루트 `subprojects {}` 에 공통 플러그인·의존성 |
| 저장소 | **PostgreSQL** (가변 스키마 영역은 `jsonb`) |
| ORM | Spring Data JPA / Hibernate — **쓰기와 단건 조회** |
| 집계 조회 | `JdbcClient` 네이티브 SQL |
| 마이그레이션 | **Flyway** |
| 테스트 | JUnit5, 통합 테스트는 실제 PostgreSQL |

### 4.2 프런트

| 축 | 선택 |
|---|---|
| 런타임 / 패키지 | Node 24, pnpm |
| 빌드 | Vite |
| 프레임워크 | React 19 + TypeScript |
| 라우팅 | React Router (코드 기반) |
| 서버 상태 | **TanStack Query** |
| 클라 상태 | `useState` / Context — **상태관리 라이브러리 없이 시작** |
| 스타일 | Tailwind |
| HTTP | `fetch` 얇은 래퍼 |

#### 프런트는 하나다

앱용·관리자용으로 화면을 나누지 않는다. 사용자가 한 명이고, 모바일과 데스크탑의
기능이 동일하기 때문이다. **하나의 반응형 SPA 로 간다.**

#### 왜 이 조합인가

프런트가 약한 1인 유지보수가 전제다. 그 관점에서 각 선택의 값어치는 이렇다.

- **TanStack Query** — 가장 큰 이득. 서버 상태 캐싱·재검증을 다 가져가므로 상태관리 라이브러리가 필요 없어진다.
- **Tailwind** — CSS 파일을 따로 들고 다니지 않는다. 반응형이 유틸리티 접두사(`sm:` `md:`)로 끝난다.
- **코드 기반 라우팅** — 라우트가 열 개 남짓이라 파일 기반 라우팅의 코드 생성과 규칙을 들일 이유가 없다.
  늘어나면 그때 옮긴다.

## 5. 데이터 모델

### 5.1 왜 RDB + JSONB 인가

"관계가 필요 없으니 NoSQL" 로 보이지만, 실제로 하려는 질의가 전부 조인·집계다.

- 이 소재를 최근 몇 건에서 썼나, 어느 문항에?
- 특정 이력서 버전을 낸 회사들의 결과는?
- 서류를 통과한 공고와 탈락한 공고의 차이는?
- 마감 7일 내 + 미제출인 건은?

데이터 규모가 작아 성능으로는 어느 엔진이든 갈리지 않는다. 그래서 **질의 모양**으로 골랐다.
수평 확장은 1인 서비스에 무의미하고, NoSQL 의 남은 이점인 스키마 유연성은 `jsonb` 가 흡수한다.

**PostgreSQL 을 고른 이유**(SQLite 아니고): 운영 비용은 SQLite 가 더 싸지만
나중에 다른 사람에게 열 여지를 남기면 동시 쓰기에서 걸린다. 컨테이너 하나 / `pg_dump` 한 줄이면
1인 운영 부담도 충분히 낮다. 공고 본문 검색까지 같은 엔진에서 끝나는 것도 이유다.

**Flyway 를 고른 이유**(`ddl-auto` 아니고): 스키마가 몇 년에 걸쳐 자라고,
아래 append-only 모델은 제약조건이 핵심인데(`UNIQUE(document_id, seq)`,
불변 컬럼의 `updatable = false`) `ddl-auto` 는 제약 변경을 따라오지 못한다.

### 5.2 설계 원칙

**조인·집계에 쓰이는 축은 컬럼으로, 회사마다 모양이 달라지는 내용물은 `jsonb` 로.**

지원서 폼은 회사마다 다르다 (500자 3문항 / 문항 없이 이력서만 / 지원동기 + 기타항목).
이 가변성은 `jsonb` 가 흡수하고, 집계 축은 컬럼으로 남아 질의가 가능하다.

### 5.3 불변 / 가변 구분

전부 append-only 로 가면 상태 전이에서 아프다. 둘로 나눈다.

| 구분 | 대상 | 규칙 |
|---|---|---|
| **불변** | `document_version`, 전형 이벤트, `submission` | 생성 후 `UPDATE` 금지. 수정 = 새 행 insert |
| **가변** | `document.head_version_id`, 지원 건의 현재 상태 | 포인터와 현재 상태만 갱신 |

가변 쪽도 이벤트에서 파생시키는 이벤트 소싱이 가능하지만 1인 서비스에 그 복잡도는 과하다.
**현재 상태는 컬럼이 들고, 이력은 이벤트 테이블이 갖는다.**

### 5.4 테이블 스케치

> 컬럼 상세·제약·인덱스는 Flyway 마이그레이션 작성 시 확정한다. 여기서는 관계와 성격만 고정한다.

```
users              (id, name, phone, email, title, created_at, updated_at)
                     └ 이름·휴대폰·이메일이 한 사람을 식별한다.
                       다만 PK 로 쓰지 않는다 — 연락처는 바뀌는 값이라
                       PK 로 삼으면 바뀔 때마다 모든 FK 가 깨진다.
                       식별 의미는 UNIQUE 제약이, 참조는 대리키 id 가 맡는다.

company            (id, name, group_name, domain, created_at)
                     └ group_name: 계열 집계용

posting            (id, company_id, title, source_url, deadline_at,
                    raw_md, parsed jsonb, created_at)
                     └ raw_md : 붙여넣은 공고 원문 그대로 보존
                     └ parsed : 경력 연차·스택·전형 절차 등 추출 결과

jobapplication     (id, posting_id, is_reapply, applied_at,
                    current_stage, outcome, created_at, updated_at)   ← 가변
                     └ 지원 건 하나. 재지원은 별도 행

stage_event        (id, jobapplication_id, stage, result, occurred_at, note_md)  ← 불변
                     └ 서류제출 / 서류합격 / 과제 / 1차면접 / 최종 / 탈락 …

episode            (id, title, summary_md, metrics jsonb, created_at, updated_at)
                     └ 재사용 단위 소재 (경력 에피소드)
                     └ metrics : 수치 + 측정 주체

episode_usage      (id, episode_id, jobapplication_id, question_key, used_at)   ← ★ 핵심 조인
                     └ 어느 소재를 어느 지원 건의 어느 문항에 썼는지

document           (id, user_id, kind, name, head_version_id,
                    created_at, updated_at)                            ← 가변(포인터)
                     └ kind: RESUME 등. 필요해질 때 추가한다

document_version   (id, document_id, seq, html, data jsonb,
                    change_note, created_at)                            ← 불변
                     └ UNIQUE(document_id, seq)
                     └ change_note : "무엇을 왜 바꿨나"

submission         (id, jobapplication_id, document_version_id,
                    answers jsonb, submitted_at)                        ← 불변
                     └ 실제 제출 스냅샷. 어느 버전을 어디에 냈는지 FK 로 고정
```

## 6. 백엔드 구조

```
com.carrepo
├── user/         사용자 식별과 프로필
├── document/     이력서·포트폴리오와 그 버전
├── posting/      공고
├── jobapplication/  지원 건과 전형 이력
├── episode/      소재와 사용 이력
├── analytics/    집계. 읽기 전용, JdbcClient 네이티브 SQL
└── common/       config / exception / audit
```

### 6.1 레이어 우선이 아니라 기능 우선인 이유

애그리거트가 하나뿐이면 `domain/` `service/` `web/` 레이어 우선이 잘 돌아간다.
커리포는 애그리거트가 여러 개다. 같은 방식이면 `domain/` 에 파일이 섞이고,
기능 하나 고치는 데 여러 패키지를 왕복하게 된다.

한 기능 안에 Controller · Service · Repository · 엔티티 · DTO 를 함께 둔다.
**다른 기능의 API 를 자기 Controller 에 얹지 않는다.**
주소가 `/api/users/{id}/resume` 라고 해서 `user` 의 기능이 되는 것은 아니다.

### 6.2 이름 충돌 회피

"지원 건"을 `application` 이라 부르면 `application.yml`, `@SpringBootApplication`,
"애플리케이션 레이어" 와 계속 섞인다. **`jobapplication` 을 쓴다.** UI 표기는 "지원".

### 6.3 기능 사이에는 엔티티를 넘기지 않는다

ID 나 필요한 입력 값만 작은 데이터 객체로 건넨다.

```kotlin
// 하지 않는다
fun render(user: User): String

// 한다
fun render(header: ResumeHeaderData): String
```

의존은 한 방향으로만 흐른다. 변환에 딸린 책임도 넘기는 쪽이 갖는다 —
전화번호 표기는 `user` 가 만들어서 건넨다.

거대한 계층이나 포트 인터페이스는 필요 없다. **외부 의존이 생기는 지점만** 포트로 감싼다.
현재 후보는 둘: PDF 렌더러, 지원 문구 생성용 LLM(붙인다면).

### 6.4 쓰기 / 읽기 경로 분리

`answers @> '{…}'`, `jsonb_path_exists` 같은 연산은 JPQL 로 표현되지 않는다.
그런데 실제로 하고 싶은 질의 — 전형 집계, 소재 재사용 추적 — 가 전부 그쪽이다.

| 경로 | 수단 | 위치 |
|---|---|---|
| 쓰기 / 단건 조회 | Spring Data JPA | 각 기능 패키지의 `*Repository` |
| 집계 / 분석 / JSONB 질의 | `JdbcClient` 네이티브 SQL | `analytics/` |

`@Query` JPQL 에 전부 밀어넣으려 하면 금방 벽을 만난다. 처음부터 나눠 둔다.

### 6.5 공통화는 두 번째 중복부터

- 공통 `BaseEntity` 를 미리 만들지 않는다.
- 범용 CRUD 서비스·컨트롤러를 만들지 않는다.
- 모든 응답을 감싸는 공통 응답 객체를 만들지 않는다.
- 미래 기능용 패키지·테이블·enum 값을 미리 만들지 않는다.

`common` 에는 설정, 예외 처리, 정말 범용적인 기술 코드만 둔다.
**도메인 규칙이 `common` 으로 옮겨가기 시작하면 경계가 무너진 신호다.**

## 7. 프런트 구조

```
web/src/
├── routes/          화면 조립만
├── features/        user / document / posting / jobapplication / episode
│   └── <도메인>/     api.ts · queries.ts · types.ts · components
├── components/ui/   범용 UI
└── lib/             API 클라이언트 등 기술 공통
```

### 7.1 2계층으로 가는 이유

엔티티가 수십 개인 프로젝트라면 `routes → features → entities → shared` 같은
4계층 분리가 값을 한다. 커리포는 도메인이 다섯 개다.
같은 방식이면 폴더 수만 배로 늘고 얻는 게 없다.

화면도 폭별로 나누지 않는다. 모바일용 컴포넌트와 데스크탑용 컴포넌트를 따로 두면
기능 하나를 두 번 고쳐야 하고, 그 순간 "기능이 동일하다"가 깨진다.
**같은 컴포넌트가 폭에 따라 레이아웃을 바꾼다.** 입력이 많은 화면은 좁은 폭에서
단을 접어 세로로 쌓고, 표는 좁은 폭에서 카드로 바꾼다.

### 7.2 규약

- **캐시 키와 fetcher 는 같이 둔다** — `features/<도메인>/queries.ts` 에.
  "키와 fetcher 는 항상 같이 바뀐다."
- **서버 데이터를 클라이언트 상태로 복사하지 않는다** — Query 캐시가 단일 출처.
- **브라우저 코드는 API 주소를 모른다** — `/api/...` 상대 경로. dev 는 프록시, 배포는 같은 jar.
- 파일명 **kebab-case**, 타입에 `I`/`T` 접두사 금지, Props 는 `{Component}Props`.

## 8. 산출물 (HTML → PDF)

이력서·포트폴리오는 HTML 로 작성하고, 원할 때 PDF 로 내려받는다.
저장은 `document_version.html` 한 컬럼이면 된다.

**HTML 은 직접 작성하거나 생성한다. WYSIWYG 편집기를 만들지 않는다** —
이 프로젝트에서 가장 비싼 프런트 작업이고, 코드 편집 + 미리보기로 충분하다.

변환은 **print CSS(`@media print`) + 브라우저 인쇄로 시작**한다.

- 네이티브 의존이 0 이다.
- 모바일 브라우저도 "PDF 로 저장" 을 지원한다.
- 대신 여백·헤더가 브라우저마다 조금씩 다르다.

A4 2 페이지 같은 레이아웃 제약이 있으므로, 실제로 제출본이 깨지는 게 확인되면
**Playwright/Chromium 렌더러를 별도 Gradle 모듈(`pdf-worker`)로 떼어낸다.**
포트 뒤에 두므로 본체 수정은 없고, 무거운 의존이 본체 이미지로 들어오지 않는다.

**앱 UI 의 디자인 톤을 이력서 산출물에 적용하지 않는다.**
산출물은 채용 담당자가 보고 인쇄되는 문서다. 경계를 분명히 긋는다.

## 9. 테스트

- 단위: 전이 규칙, 소재 재사용 판정, 렌더링 등 순수 로직
- 통합: `integration/` 분리 + **실제 PostgreSQL**
- 픽스처: `support/` 패키지. **실명·실제 연락처를 쓰지 않는다.**

**H2 를 테스트에 쓰지 않는다.** prod 가 PostgreSQL 인데 테스트만 H2 면
`jsonb` 연산자와 Flyway 마이그레이션이 검증되지 않고 조용히 갈라진다.

프런트는 완료 조건을 `pnpm --dir web build`(tsc 포함) 통과로 둔다.

## 10. 단계

전부 한 번에 만들지 않는다. **V2 에 도달해야 파일로 관리하던 것보다 나아진다** —
V1 만 만들고 멈추면 손해다. 그래서 V1 은 최대한 얇게 간다.

| 단계 | 내용 |
|---|---|
| V1 | 사용자 · 공고 · 지원 건 · 전형 이력 · 내보내기 |
| **V2** | 소재 라이브러리 · 문항 초안과 버전 · **소재 사용 이력** ← 본전 지점 |
| V3 | 이력서 본문 · 제출본 고정 · 첨부 |
| V4 | 집계 (지원 건이 충분히 쌓인 뒤) |

`analytics` 는 데이터가 쌓이기 전엔 값이 0 이고 질의를 설계할 수조차 없다.
패키지 자리만 잡아두고 V4 까지 만들지 않는다.

---

## 11. 데이터 소유권

기존에 마크다운 파일로 모아둔 자료가 첫 시드 데이터다. 다만 형식이 제각각이라
일괄 파서를 만들 가치는 낮다. **반자동 이관(붙여넣기 + 손보정)을 전제로 하고,
일괄 마이그레이션 도구는 만들지 않는다.**

반대 방향은 반드시 만든다. **전체 내보내기(마크다운 + JSON + 첨부의 ZIP)는 V1 필수다.**

> 개인 커리어 데이터는 서비스보다 오래 살아야 한다.
> **"커리포를 그만 써도 내 데이터는 남는다"** 가 제품 원칙이다.

백업도 같은 수단으로 해결된다 — 내보내기 ZIP + `pg_dump`.
