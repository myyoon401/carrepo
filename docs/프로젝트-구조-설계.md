## 1. 서비스 정의

지원 공고를 모아두고, 이력서·지원 문구를 만들어 저장하고, 전형 결과까지 쌓아
**다음 지원에 재활용하는 개인 커리어 저장소**.

공고 수집은 외부 채용 사이트에 의존한다. 커리포는 **붙여넣은 이후**를 담당한다.

### 기존 작업 방식에서 출발

`기존 마크다운 작업 디렉터리`에서 이미 손으로 하고 있는 일이 그대로 요구사항이다.

| 지금 (md 디렉터리) | 커리포에서 |
|---|---|
| 회사별 폴더 + `공고.md` / `자기소개서.txt` / `제출본.txt` / `면접복기.md` | candidacy 한 건에 묶인 레코드 |
| 지원 이력 표 수기 표 (2026-07 이후 갱신 중단) | candidacy 조회로 자동 생성 |
| 전적 기록 수기 집계 (도메인별 전패, 탈락 단계 분류) | analytics 읽기 질의 |
| 파일명 버전 관리 (`resume_v16`, `_수정본`, `_최종`) | `document_version` 행 + `submission` FK |
| "이전 제출 소재였던 X, Y, Z는 사용하지 않았습니다" (수기 기억) | `episode_usage` 조인 |

마지막 항목이 커리포의 존재 이유다. 이게 없으면 마크다운 뷰어와 다를 게 없다.

### 사용 환경

**반응형 웹.** 모바일과 데스크탑에서 **기능이 동일하다.** 어느 쪽이 읽기 전용이라거나
특정 기능이 한쪽에만 있지 않다. 공고 등록·문구 작성·이력서 편집 전부 양쪽에서 된다.
화면 폭에 따라 레이아웃만 달라진다.

따라서 화면을 둘로 나누지 않는다. → [4.2](#42-프런트는-하나다)

## 2. 전체 구조

```
carrepo/
├── settings.gradle.kts          include("backend")
├── build.gradle.kts             루트: subprojects 공통 플러그인·의존성
├── backend/                     Kotlin + Spring Boot    (:8080)
│   └── src/main/kotlin/com/carrepo/…
├── web/                         Vite + React            (:5173, dev 전용)
│   ├── package.json
│   └── src/
├── docs/
└── docker-compose.yml           PostgreSQL
```

모노레포 도구(Turborepo·Nx·pnpm workspace)는 **쓰지 않는다.** 패키지가 둘뿐이고
서로 코드를 공유하지 않는다. Gradle이 backend를, pnpm이 web을 각자 맡는다.

### 2.1 설계 기준

**서버 하나 띄우면 백엔드도 프런트도 다 보일 것.** 이게 모노레포로 가는 유일한 이유다.
구조적 완성도를 명분으로 복잡도가 올라가는 건 거부한다.
판단 기준은 **"혼자서, 프런트가 약한 상태로, 1년 뒤에도 고칠 수 있나"**.

## 3. 실행과 배포

### 개발

```bash
docker compose up -d            # PostgreSQL
./gradlew :backend:bootRun      # :8080
pnpm --dir web dev              # :5173  — /api/* 를 8080 으로 프록시
```

브라우저 코드는 API 주소를 모른다. 항상 같은 출처의 `/api/...` 상대 경로로 부르고,
dev에서는 Vite 프록시가 8080으로 넘긴다. **CORS 설정이 필요 없다.**

### 배포

```bash
./gradlew build                 # web/dist 를 jar 의 static/ 에 넣는다
java -jar backend/build/libs/carrepo.jar
```

**산출물은 jar 하나, 프로세스 하나.** 배포에서는 Spring이 정적 리소스를 직접 서빙하므로
프록시도 게이트웨이도 없다. `참고 프로젝트 C`이 WAR 하나로 뜨던 성질을 그대로 가져온 것이다.

연결 비용은 Gradle `Exec` 태스크 한 개(`pnpm build` 실행 + `dist` 복사) 정도다.
node-gradle 플러그인은 들이지 않는다.

## 4. 기술 스택

### 4.1 백엔드

레퍼런스: `참고 프로젝트 A`

| 축 | 선택 |
|---|---|
| 언어 / 런타임 | Kotlin 2.2.x, Java 21 toolchain |
| 프레임워크 | Spring Boot 4.1.x |
| 빌드 | Gradle, 루트 `subprojects {}`에 공통 플러그인·의존성 |
| 저장소 | **PostgreSQL** (가변 스키마 영역은 `jsonb`) |
| ORM | Spring Data JPA / Hibernate — **쓰기 전용** |
| 조회 | `JdbcClient` 네이티브 SQL — **집계·분석 전용** |
| 마이그레이션 | **Flyway** |
| 테스트 | JUnit5 + Kotest assertions, 통합은 **Testcontainers Postgres** |

### 4.2 프런트

레퍼런스: `참고 프로젝트 B` (스택) · `참고 프로젝트 D` (참고만)

| 축 | 선택 |
|---|---|
| 런타임 / 패키지 | Node 24, pnpm |
| 빌드 | Vite |
| 프레임워크 | React 19 + TypeScript |
| 라우팅 | TanStack Router (파일 기반) |
| 서버 상태 | **TanStack Query** |
| 클라 상태 | `useState` / Context — **상태관리 라이브러리 없이 시작** |
| 스타일 | Tailwind 4 + shadcn(radix) |
| HTTP | `fetch` 얇은 래퍼 |

#### 프런트는 하나다

`참고 프로젝트 B`는 `app-web`과 `admin-web`을 나눴다. 웹뷰로 네이티브에 들어가고,
백오피스가 별도로 필요하고, 팀이 나눠 작업하기 때문이다. 커리포는 셋 다 해당 없다.
**하나의 반응형 SPA로 간다.**

#### 왜 이 조합인가

프런트가 약한 1인 유지보수가 전제다. 그 관점에서 각 선택의 값어치는 이렇다.

- **TanStack Query** — 가장 큰 이득. 서버 상태 캐싱·재검증을 다 가져가므로 상태관리 라이브러리가 필요 없어진다.
- **Tailwind + shadcn(radix)** — CSS를 직접 쓰지 않고 컴포넌트를 복사해서 쓴다. 반응형이 유틸리티 접두사(`sm:` `md:`)로 끝나고, radix 컴포넌트가 터치·키보드 입력을 모두 처리한다. 디자인 감각 없이도 양쪽에서 멀쩡한 화면이 나온다 — "백엔드 개발자가 혼자 프런트를 유지"의 핵심.
- **TanStack Router 파일 기반** — 파일을 놓으면 라우트가 되고 타입이 따라온다.

#### `참고 프로젝트 D`을 따르지 않는 이유

React 16.8 + CRA + redux + styled-components 4 + tslint, `containers/` ↔ `components/` 분리.
2019년 구조다. 손에 익은 코드지만 **패턴을 가져올 대상은 아니다.**

## 5. 데이터 모델

### 5.1 왜 RDB + JSONB인가

처음엔 "관계가 필요 없으니 NoSQL"로 보였지만, md 디렉터리에서 실제로 하는 질의가 전부 조인·집계였다.

- 이 소재를 최근 몇 건에서 썼나, 어느 문항에?
- 특정 이력서 버전을 낸 회사들의 결과는?
- 서류를 통과한 공고와 탈락한 공고의 차이는?
- 마감 7일 내 + 미제출인 건은?

데이터 규모가 작아 성능으로는 어느 엔진이든 갈리지 않는다. 그래서 **질의 모양**으로 골랐다.
수평 확장은 1인 서비스에 무의미하고, NoSQL의 남은 이점인 스키마 유연성은 `jsonb`가 흡수한다.

**Postgres를 고른 이유**(SQLite 아니고): 운영 비용은 SQLite + Litestream이 더 싸지만
나중에 다른 사람에게 열 여지를 남기면 동시 쓰기에서 걸린다. 컨테이너 하나 / `pg_dump` 한 줄이면
1인 운영 부담도 충분히 낮다. 공고 본문 전문검색까지 같은 엔진에서 끝나는 것도 이유다.

**Flyway를 고른 이유**(`ddl-auto: update` 아니고): 레퍼런스의 `ddl-auto`는 설치 없이 돌아야 하는
과제 제출물이라 성립한 선택이다. 커리포는 몇 년 굴리며 스키마가 자라고, 아래 append-only 모델은
제약조건이 핵심인데(`UNIQUE(document_id, seq)`, 불변 컬럼의 `updatable = false`)
`ddl-auto`는 제약 변경을 따라오지 못한다.

### 5.2 설계 원칙

**조인·집계에 쓰이는 축은 컬럼으로, 회사마다 모양이 달라지는 내용물은 `jsonb`로.**

회사마다 지원서 폼이 다르다 (A사 = 500자 3문항 / B사 = 문항 없이 이력서만 /
C사 = 지원동기 + 기타항목). 이 가변성은 `jsonb`가 흡수하고, 집계 축은 컬럼으로 남아 질의가 가능하다.

### 5.3 불변 / 가변 구분

전부 append-only로 가면 상태 전이에서 아프다. 둘로 나눈다.

| 구분 | 대상 | 규칙 |
|---|---|---|
| **불변** | `document_version`, `candidacy_event`, `submission` | 생성 후 `UPDATE` 금지. 수정 = 새 행 insert |
| **가변** | `document.head_version_id`, `candidacy.current_stage` / `outcome` | 포인터와 현재 상태만 갱신 |

가변 쪽도 `candidacy_event`에서 파생시키는 이벤트 소싱이 가능하지만 1인 서비스에 그 복잡도는 과하다.
**현재 상태는 컬럼이 들고, 이력은 이벤트 테이블이 갖는다.**

### 5.4 테이블 스케치

> 컬럼 상세·제약·인덱스는 Flyway 마이그레이션 작성 시 확정한다. 여기서는 관계와 성격만 고정한다.

```
company            (id, name, group_name, domain, created_at)
                     └ group_name: 계열 집계용 (CJ 계열, 카카오 계열 …)

posting            (id, company_id, title, source_url, deadline_at,
                    raw_md, parsed jsonb, created_at)
                     └ raw_md : 붙여넣은 공고 원문 그대로 보존
                     └ parsed : 경력 연차·스택·전형 절차 등 추출 결과

candidacy          (id, posting_id, is_reapply, applied_at,
                    current_stage, outcome, version, created_at, updated_at)   ← 가변
                     └ 지원 건 하나. 재지원은 별도 행 (is_reapply = true)

candidacy_event    (id, candidacy_id, stage, result, occurred_at, note_md)     ← 불변
                     └ 서류제출 / 서류합격 / 과제 / 1차면접 / 최종 / 탈락 …
                     └ note_md : 면접 복기를 여기에 붙인다

episode            (id, title, summary_md, metrics jsonb, created_at, updated_at)
                     └ 재사용 단위 소재. "비밀번호 암호화 트리거 이관" 등
                     └ metrics : 4,200 TPS / 27.6% 같은 수치 + 측정 주체

episode_usage      (id, episode_id, candidacy_id, question_key, used_at)       ← ★ 핵심 조인
                     └ 어느 소재를 어느 지원 건의 어느 문항에 썼는지

document           (id, kind, name, head_version_id, created_at, updated_at)   ← 가변(포인터)
                     └ kind: RESUME / PORTFOLIO

document_version   (id, document_id, seq, html, data jsonb,
                    change_note, created_at)                                    ← 불변
                     └ UNIQUE(document_id, seq)
                     └ html : 산출물 본문. data : 구조화 데이터
                     └ change_note : "무엇을 왜 바꿨나" (작업메모가 하던 일)

submission         (id, candidacy_id, document_version_id,
                    answers jsonb, submitted_at)                                ← 불변
                     └ 실제 제출 스냅샷. 어느 버전을 어디에 냈는지 FK로 고정
                     └ answers : 문항별 제출 본문 (초안 아님)
```

### 5.5 이 모델이 해결하는 것

- 지원 이력 표 표가 7월에 멈춘 문제 → candidacy 조회로 항상 최신
- 이력서 버전 계보가 파일명에만 있던 문제 → `UNIQUE(document_id, seq)` + `submission` FK
- 초안과 제출본이 다른 파일로 흩어진 문제 → `submission`이 제출본을 못 박음
- 소재 재사용을 기억에 의존하던 문제 → `episode_usage` 한 줄 질의

## 6. 백엔드 구조

```
com.carrepo
├── posting/      Posting.kt, PostingService.kt, PostingController.kt, PostingRepository.kt
├── candidacy/    Candidacy.kt, CandidacyStatus.kt, CandidacyEvent.kt, …
├── episode/      Episode.kt, EpisodeUsage.kt, …
├── document/     Document.kt, DocumentVersion.kt, Submission.kt, …
├── analytics/    전적표. 읽기 전용, JdbcClient 네이티브 SQL
└── common/       config / exception / audit
```

### 6.1 레이어 우선이 아니라 기능 우선인 이유

레퍼런스는 애그리거트가 `Transfer` **하나**라서 `domain/` `application/` `web/` 레이어 우선이 잘 돌아갔다.
커리포는 애그리거트가 8개다. 같은 방식이면 `domain/`에 파일이 15개 섞이고,
기능 하나 고치는 데 6개 패키지를 왕복하게 된다.

### 6.2 이름 충돌 회피

"지원 건"을 `application`이라 부르면 레이어 이름과 정면으로 부딪힌다
(`com.carrepo.application.application.ApplicationService`).
**`application`은 레이어 이름으로도 도메인 이름으로도 쓰지 않는다.**
도메인 명칭은 잠정적으로 `candidacy`. → [미결정](#미결정)

### 6.3 port / adapter는 범위를 좁힌다

레퍼런스가 `port.outbound` + `adapter.outbound.gateway`를 둔 건 `mock-bank-server`라는
진짜 외부 시스템이 있었기 때문이다. 커리포 백엔드는 대부분 CRUD라서 전부에 포트를 씌우면
기능 하나당 의미 없는 파일이 3개씩 늘어난다.

**외부 의존이 생기는 지점만 포트로 감싼다.** 현재 후보는 둘: PDF 렌더러, 지원 문구 생성용 LLM(붙인다면).

### 6.4 쓰기 / 읽기 경로 분리

`answers @> '{…}'`, `jsonb_path_exists` 같은 연산은 JPQL로 표현되지 않는다.
그런데 커리포가 실제로 하고 싶은 질의 — 전적표식 집계, 소재 재사용 추적 — 가 전부 그쪽이다.

| 경로 | 수단 | 위치 |
|---|---|---|
| 쓰기 / 단건 조회 | Spring Data JPA | 각 기능 패키지의 `*Repository` |
| 집계 / 분석 / JSONB 질의 | `JdbcClient` 네이티브 SQL | `analytics/` |

`@Query` JPQL에 전부 밀어넣으려 하면 금방 벽을 만난다. 처음부터 나눠 둔다.

### 6.5 엔티티 규약

**엔티티 캡슐화 + 상태 전이 검증.** `private var` + 공개 `val` getter로 변경 경로를 좁히고,
전이는 `transitionTo()` 안에서 허용 여부를 검증한다.

레퍼런스의 `TransferStatus.canTransitionTo()`가 하던 일이 커리포의 전형 단계 전이와 구조가 같다.
전적 기록가 "특정 단계에서 반복해 탈락", "과제 탈락을 하나로 묶으면 안 된다 — 종류가 서로 다르다"처럼
**단계를 정확히 구분해서 보려 하고 있으므로**, 그 구분을 enum + 전이 규칙으로 DB에 강제하면
analytics 집계가 따로 노력 없이 나온다.

그 외: `@Column(comment = …)` 명시 · `AuditingEntityListener` · `@Version` · `open-in-view: false` ·
관심사별 `@ConfigurationProperties` 분리 · 에러코드 enum + `@RestControllerAdvice` 단일 번역 지점.
주석은 "무엇"이 아니라 **"왜"**를 적는다.

## 7. 프런트 구조

```
web/src/
├── routes/          TanStack Router 파일 기반. 화면 조립만
├── features/        posting / candidacy / episode / document / analytics
│   └── <도메인>/     api.ts · queries.ts · types.ts · components/
├── components/ui/   shadcn 컴포넌트
└── shared/          lib / hooks / utils / types
```

### 7.1 2계층으로 가는 이유

`참고 프로젝트 B`는 `routes → features → entities → shared` 4계층을 ESLint로 강제한다.
entity가 18개라 그 경계가 값을 했다. 커리포는 도메인이 5개다.
같은 방식이면 폴더 수만 배로 늘고 얻는 게 없다.

**`features/<도메인>` + `shared/`로 간다.** 도메인이 자라면 그때 쪼갠다.

화면도 폭별로 나누지 않는다. 모바일용 컴포넌트와 데스크탑용 컴포넌트를 따로 두면
기능 하나를 두 번 고쳐야 하고, 그 순간 "기능이 동일하다"가 깨진다.
**같은 컴포넌트가 폭에 따라 레이아웃을 바꾼다.** 입력이 많은 화면(이력서 편집, 문구 작성)은
좁은 폭에서 단을 접어 세로로 쌓고, 표(전적표·지원 목록)는 좁은 폭에서 카드로 바꾼다.

### 7.2 가져오는 규약

- **캐시 키와 fetcher는 같이 둔다** — `features/<도메인>/queries.ts`에 `queryKey`와 `queryFn`을 함께.
  참고 프로젝트 B 규칙 중 가장 값어치 있는 것. "키와 fetcher는 항상 같이 바뀐다."
- **서버 데이터를 클라 상태로 복사하지 않는다** — TanStack Query 캐시가 단일 출처.
- **브라우저 코드는 API 주소를 모른다** — `/api/...` 상대 경로. dev는 프록시, 배포는 같은 jar.
- 파일명 **kebab-case**, 타입에 `I`/`T` 접두사 금지, Props는 `{Component}Props`.
- 라우트 전용 부품 폴더는 밑줄이 아니라 하이픈(`-components/`) — TanStack Router에서 밑줄은 pathless layout.

### 7.3 덜어내는 것

| 항목 | 판단 |
|---|---|
| 앱/어드민 2개 분리 | 하나의 반응형 SPA로 |
| 4계층 + ESLint 레이어 강제 | 2계층. 규약은 문서로 — 혼자 쓰는데 코드로 강제할 이유가 없다 |
| Zustand | 처음엔 뺀다. 참고 프로젝트 B CLAUDE.md도 "store부터 만들지 말라"고 적고 있다 |
| i18n (`use-intl`, 4개국어) | 한국어만 |
| 웹뷰 브릿지 · 토큰 리프레시 인터셉터 | 네이티브 없음. 1인 인증은 훨씬 단순 |
| axios + 프로젝트 간 코어 동기화 | `fetch` 얇은 래퍼로 충분 |

## 8. 산출물 (HTML → PDF)

이력서·포트폴리오는 HTML로 작성하고, 원할 때 PDF로 내려받는다.
저장은 `document_version.html` 한 컬럼이면 된다.

변환은 **print CSS(`@media print`) + 브라우저 인쇄로 시작**한다.

- 네이티브 의존이 0이다.
- 모바일 브라우저도 "PDF로 저장"을 지원한다.
- 대신 여백·헤더가 브라우저마다 조금씩 다르다.

작업메모에 "A4 2p", "PDF 텍스트 이력서 필수(D사은 PDF 필수 명시)" 같은
레이아웃 제약이 기록돼 있으므로, 실제로 제출본이 깨지는 게 확인되면
**Playwright/Chromium 렌더러를 별도 Gradle 모듈(`pdf-worker`)로 떼어낸다.**
포트 뒤에 두므로 본체 수정은 없고, 무거운 의존이 본체 이미지로 들어오지 않는다.

## 9. 테스트

- 단위: 도메인 전이 규칙(`CandidacyStatus`), 소재 재사용 판정 등 순수 로직
- 통합: `integration/` 분리 + **Testcontainers Postgres**
- 픽스처: `support/` 패키지

**H2를 테스트에 쓰지 않는다.** prod가 Postgres인데 테스트만 H2면
`jsonb` 연산자와 Flyway 마이그레이션이 검증되지 않고 조용히 갈라진다.
레퍼런스가 H2를 쓴 건 설치 없이 돌아야 하는 과제였기 때문이다.

프런트는 완료 조건을 `pnpm lint && pnpm typecheck && pnpm build` 통과로 둔다.

## 11. 기존 데이터 이관

`기존 마크다운 작업 디렉터리`에 이미 기존 자료가 있다
(회사별 폴더 여러 개, 지원 이력 수십 건 + 전적표, 이력서 여러 버전).
**이게 첫 시드 데이터다.** 다만 형식이 제각각이라 일괄 파서를 만들 가치는 낮다.

→ 반자동 이관(붙여넣기 + 손보정)을 전제로 하고, 일괄 마이그레이션 도구는 만들지 않는다.
   단, 이관 중 발견되는 필드는 `jsonb` 쪽으로 흡수해 스키마를 자주 바꾸지 않는다.
